# Threat model: the operator

This file covers the operator side. It says what the operator can see and do, what limits that, and what it cannot promise. The testnet deployment holds test funds only, the contract has had no independent review, and the anonymity set is small and made of test notes.

## What the operator sees

- **Requests.** Each lease request carries a proof, a nullifier and a bound class. The operator sees those, the times it handled them and the charge it signs.
- **Prompts.** Chat bodies are encrypted end to end to the model's key from the attestation report. The operator sees the model name, sizes and timing, not the text. It forwards the encryption headers and refuses a request that has none.
- **Addresses.** Operator code reads no client address and keeps none, and nothing it writes to its database or its alarm messages holds an IP address or a prompt (a test checks this). The entry point is a different matter: Tailscale Funnel's relay sees the client address and the time of every connection and passes the address to the laptop in a header. The operator does not read that header. A client that connects through Tor shows a Tor exit instead. If Funnel cannot carry a feature, a Cloudflare Tunnel takes its place and then terminates TLS, so Cloudflare sees request metadata; bodies stay encrypted.
- **Linking.** Tor exits repeat, and timing and usage can still link a user's requests. The set of notes a lease could belong to is the set of open notes, which on testnet is small.

## What the provider sees

NEAR AI receives each request under a per-lease key that the operator mints and caps at the lease bound. The provider sees the model, token counts, timing and the key's usage, and can tie requests of one lease together. It does not see which note the lease belongs to. Prompts reach it only as ciphertext addressed to the model's attested key.

## What the logs keep

The operator writes no log lines that come from a request; its error output holds start-up errors and, after a panic, the source line only. Lease records hold the nullifier, the lease token's hash, the bound, the charge, the usage reading and times; at settlement the key id and the exact timers are deleted and times fall back to the hour. Copies on the second machine carry hour-rounded times from the start. Request proofs and signed states are deleted after 44 days, on both machines. Alarm messages pass through a scrubber that removes `sk-` and `rpt-` strings, `Bearer` credentials and `Authorization` values.

## Processes and keys

The operator runs as five processes under one dedicated macOS user: the public API, a key minter, a signer, a closer and a watcher. The public API has no NEAR key and no login; it holds the provider keys of the leases that are open, in memory, each capped at its lease bound. The NEAR AI login lives only in the key minter. The state and clearance keys exist only in the signer, from two passphrases typed at start-up. The closer holds one function-call key, `mutual_close`; the signer's is `heartbeat`; the watcher holds the upkeep key and a separate exit-answer key. Processes talk over Unix sockets (mode 0600, checked by user id), and on the laptop the public API is the only TCP listener. The replica on the second machine also listens on TCP.

The processes share one macOS user, so code execution in any one of them as that user can read every file that user can read, including the sealed login file once its passphrase is known. The separation limits what a bug in the web-facing process can reach in memory and which keys it holds; it does not stop an attacker who gets a shell as the service user. The developer tools and browsers installed on the laptop stay readable by every user on macOS.

Usage figures come from NEAR AI's `usage/history` for a lease's key, read with the session login of the key minter, because the read-only reporting routes answer 404. Reading usage therefore uses the same login that can mint keys, and it stays inside the minter process.

## The second machine

The operator signs a state only after a second machine has the record on disk, so a lost laptop disk does not let a user spend a state twice. The second machine sits in the same home as the laptop: it covers a lost disk or a dead laptop, not a power or network failure of the house, and it does not protect against someone who takes both machines. It holds the log, a watcher and its own exit-answer key, and no signing key and no provider token. The operator signs each log entry it sends, and the second machine pins that key. Since 5 November 2026 the second machine is a MacBook Air on the same tailnet (a tag and an access rule admit only the operator's machine), running the replica, the second watcher and a dead-man switch; the operator refuses to sign while the replica cannot be reached, so a sleeping or powered-off Air stops new leases (seen on 6 November 2026) until it is back. The public status lists only the first machine's watcher. FileVault is off on the Air, so anyone who holds the machine can read the log on its disk. The dead-man switch runs in the same house, so an external check from GitHub Actions asks the public status every 30 minutes as a second alarm path.

## If the operator is offline

A user leaves with `request_exit` and, once the 7-day window has passed, `finalize_exit`, and the vault does not need the operator for that. If the operator and every watcher are offline for the whole window, nobody can answer an exit from an old state, so the user leaves with an older, higher balance than the real one. The loss falls on the operator, and the cap on open deposits bounds it.

## If a key leaks

New leases and clearances stop at once (`emergency`) and `/v1/status` shows why; users are told to exit and a new vault is deployed. A leaked state key lets an attacker sign states, a leaked clearance key lets an attacker forge clearances, and a leaked provider credential lets an attacker spend the prepaid credit. None of these gives access to user funds held by the vault, whose rules are in the contract.

## What closing and exiting show, from the web app

A close, an exit request and a finalize name the note ID in the vault call, and a payout names the payout account. A close also shows the note's total spend and the payout account. An exit request also shows the note's balance and concession, and a finalize shows the amount paid. The web app sends them from the wallet account the user connects, so that account is on chain next to the note ID; connecting an account other than the funding account keeps the two apart, and the app does not create one. `request_exit` and `finalize_exit` can come from any account with a little NEAR, and the payout still goes to the account fixed at deposit.

The RPC provider sees the user's IP address with every read the app makes to leave: the sending account's balance, `exit_requests` (a page of the whole list, naming no note), `note_records` (names the note ID) and `pending_payout` (names the payout account). The browser cannot use Tor.

A close asks the operator for a clearance, so the operator sees the ownership proof and the user's IP address and the time. `nymirad` waits a random one to twenty minutes first; the web app does not, so a close soon after a conversation is easier to tie to it. A close handed to the operator's intake shows the operator's account as the sender, and the operator keeps its close fee.

An exit from an old state can be defeated: if the user loses the latest state (the browser's storage and the backup), the operator can answer the exit with a later request and keep what it charged, up to the whole remaining balance. The close screen says so next to the guarantee.

## What closing and exiting show on chain

A close, an exit request and a finalize name the note's ID in the vault call, and a payout names the payout account. `nymirad` sends them from a submitter account, a separate NEAR account whose access key can call only `request_exit`, `finalize_exit`, `mutual_close` and `claim_payout` on the vault, so the account that funded the note does not sign them. The submitter's own funding trail is visible on chain: whoever funds it can be seen to have paid for gas next to your note ID.

One submitter shared by every note puts all of those notes next to one account. `nymirad` keeps one submitter per family (your personal notes, and each budget note on its own) so you can keep that link apart. A note belongs to the family `personal` until you assign another.

Sends go over Tor, each on its own circuit. If Tor is down, `nymirad` sends nothing by itself. It asks you first, in fixed words: a direct send shows your IP address to the RPC endpoint together with the note's ID and its total spend. The clearance request and the operator's close intake never go direct, because they would show your address to the operator. A close can go to the operator's intake when the submitter has no NEAR; the operator then keeps its close fee.

## Expiry and backups

A note can still close or exit after its expiry. The treasury can take it only 7 days after the later of the expiry and the last exit activity, and never while an exit is pending. By default `nymirad` opens no new lease on a note within 5 days of its expiry and tries a mutual close at 5 days. If the close has failed, it files `request_exit` at 3 days. It shows notices at 14, 7 and 2 days. The guard can be switched off. A close or exit it sends shows the note ID like any other, and it never goes direct while Tor is down. Closing every note when a session ends is a separate switch, off by default, because each close shows the note ID and the total spend.

After every retire, and after each lease open, close and deposit, `nymirad` writes the whole state, encrypted with age to a public key you chose at setup, to a copy on the machine and to a second place you name. The private key is shown once and is never stored by `nymirad`, in the keychain or beside the file. With a passphrase instead, Argon2id (64 MiB, 3 passes, 1 lane, random salt) derives the key, and the passphrase needs at least 12 characters. A passphrase can still be guessed offline by anyone who holds a backup; Argon2id slows that down and does not stop it.

Inside the encryption sit the notes and wallet states (in the clear), the submitter keys, the exit book, the lease records, the agent registry and the config, so whoever holds a backup and its key or passphrase can spend your notes. Keep the key away from the machine and from the backup. The place that stores the file sees an encrypted blob, its size and its write times.

On the machine the wallet state is sealed under the passphrase. While a wallet is open for a lease, a close or an exit, its plain files sit in a memory-backed directory (tmpfs on Linux, a RAM disk on macOS), never on the disk, and `nymirad` refuses to open the wallet if it cannot make one. A crash leaves the files in memory until the next start seals them. The operating system may still write memory to swap: macOS encrypts swap by default, Linux does not unless the machine is set up for it.

Restoring with the key or passphrase continues on the same note from the state the backup held. If a lease was served after that backup, the operator is ahead of the restored state, and the way out is an exit, which the operator can defeat by showing a later state; the balance then goes to the treasury at expiry. Restoring from the note secret alone gives an exit from the deposit state with concession 0, with the same risk.

On the operator's emergency notice `nymirad` stops opening leases and suggests an exit for each open note. It does not exit by itself because of the notice. It reads the notice from `/v1/status` before each lease and every few minutes while it runs, so a notice can reach it late.

## Budget notes for agents

A budget note has your own account as its payout account, fixed at deposit. The most a compromised agent can do with its token is spend that note on inference; it cannot withdraw it anywhere but back to you. The ceiling is the note's balance. The vault matching the client's pins is what that rests on, and the team can still update the vault code.

What is enforced by `nymirad` on your machine, not by the chain: an agent token reaches only chat and models; it draws only on its own note and your own token never picks a budget note; a disabled token is refused on its next request; with no valid signed policy every agent request is refused with 402 `policy_missing` before anything leaves the machine; a request for a model outside the policy's `allowed_models` is refused with 402 `model_not_allowed`; and the call, daily and rate limits are checked on every request, also on an open lease. The call and daily limits rest on an estimate (the cost of the sealed input at the pinned prices plus the output cap), and the counters sit in your state directory; an agent that can write there, or that runs as your OS user, can reset them. The policy's NEP-413 signature is checked on every request. The signing key is checked against your account's access keys only when you load the policy: a key you remove later does not cancel a policy already loaded (disable the agent token to stop it). These rely on the machine that runs `nymirad`.

- The agent socket's peer user ID check is the only OS-user check. Loopback TCP has none: a `tcp` token is a bearer secret for any local process that can read it.
- An agent that runs as your own OS user can read your owner token and the registry. Run it against its own `nymirad` instance with its own state directory, port and owner token that holds only its budget note.
- A forward over SSH puts the agent host's traffic on your loopback, so the agent host can send requests with the token it holds. It holds no credential for your machine when you start the forward from your side.
- Closing a budget note shows its note ID and total spend next to your named payout account, so the agent's total becomes public at the end.
- There is no remote rate limit and no remote kill switch for a budget note. A lease request carries a proof, a nullifier and a bound class and does not name the note, so the operator cannot pick one note to slow down or stop; the design is meant to keep it from grouping leases by note, a claim of the underlying protocol that has not been checked independently. Only your own `nymirad` limits an agent's rate, and only you disable its token. The operator's emergency stop and capacity limits apply to new leases in general, not to one note.
- The registry that marks budget notes is part of the encrypted state backup. A restore from a notes-only backup (the copy written at deposit time) does not carry it, and the restored budget note then counts as an ordinary note until the registry is put back.
- **Opt-in: the budget note on the agent's machine.** If you move the note with `nymirad agent move`, the note's secret and wallet go to the agent's machine and your copy stops spending. The balance is still the ceiling and the payout account is still yours, but the policy, the counters and the approvals then run on a machine you do not control, and revocation is not guaranteed. Revoking is a race: only what is unspent when your final close or exit lands goes to the payout account, a hostile agent can spend the rest on inference first, and an exit from a stale state can be defeated by a newer one. The agent's `nymirad` writes each new state, encrypted to your age key and numbered, to the places you chose; those files are only as current as the last retire and as safe as the place that holds them. `agent import-state` chooses by the nullifier chain and the operator's signature and warns when the operator already counts the best state's nullifier as used, which says the files you hold are behind. A moved note's token is a bearer secret on the agent machine's loopback.

## MCP spending tools

`mcp/` is an MCP server over stdio that gives an agent three tools: `nymira_balance`, `nymira_quote` and `nymira_ask`. It adds no authority. It holds the agent token it reads from a private file, forwards to the owner's `nymirad` over loopback or the agent socket, and every check in "Budget notes for agents" runs there. The tokens, the limits and the ceiling are the ones above.

- The agent host and its model vendor see every question and answer that passes through `nymira_ask`, and the balance, charges and timing the tools return. The privacy described elsewhere in this file does not cover the program that drives the tools.
- Rate limits are local to the owner's `nymirad`. There is no remote kill switch.
- The confirmation amount is per call, so an agent can stay under it with many smaller calls. A hard daily cap needs `max_daily_usd` or a fresh note per day.
- In opt-in mode the policy is advisory, because it runs on the agent's machine. Only the note's balance is a ceiling.
- The server cannot approve a call: approvals are signed by the owner. Text in an answer reaches the agent as untrusted text, and a prompt injection in it can still make the agent ask again, up to the limits.
- The install is checked by a hash in release notes signed with the release key, and the tarball bundles its dependencies. A host that runs a different copy of the server, or a host that edits the entry, is outside this.
- Cursor and IronClaw were not run against it; the compatibility table in `mcp/README.md` says what was.

## What the other parties see

- **The web hosts (Cloudflare Pages and the GitHub Pages mirror).** They see each visitor's IP address and which files were asked for, and they decide which code a visitor gets. A compromised host could serve a different app. `nymirad verify-web` checks each host against the manifest that the host serves, if the pinned release key signed it for this profile, over Tor and directly; its key and the two host names are compiled in, and it passed against both hosts on 5 November 2026 (Cloudflare adds one header it prints as an accepted note). It does not check that the version is the newest, so a host could serve an older signed release and pass. It checks headers on the Cloudflare host only; the mirror is checked for file bytes. It catches a change only if the user runs it, and not a host that serves different content to different clients. The manifest hashes and the release key are in the repository and the README, which a thief with the GitHub, Cloudflare and domain accounts could change; one public Sigstore Rekor entry holds the hash of a statement with the bundle hash and the key (see `web/INTEGRITY.md`), but it is not signed by the release key. No outside party has rebuilt the bundle.
- **RPC providers.** They see the IP address of whoever reads or sends, and with a deposit transaction the account, the transaction hash (so the note ID, the commitment and the payout account) and the time. The web app cannot use Tor. `nymirad` sends through Tor and asks first before any direct send.
- **Public certificate logs.** The operator's host name, which the certificate of its public entry carries, is listed in public certificate logs. They show that the name exists and when a certificate was issued, not who connects.
- **Attestation and collateral services (NEAR AI's attestation endpoint, PCCS).** They see the address that asks and the time. `nymirad` asks through Tor; the web app asks NEAR AI and Phala's PCCS directly (Intel's own collateral service sends no CORS headers).
- **Gateway compose hash not pinned.** Since version 5 the policy accepts any compose hash for the gateway role (the entry `"*"`, allowed for that role only). The gateway's TDX measurements, TCB status and signing key are still checked against the policy, but a changed gateway application image with the same measurements would not be noticed by the compose hash. The model deployment keeps exact compose hashes.
- **The web app can take a newer attestation policy from the site.** A deploy may put `attestation-policy.json` beside a release. The page uses it only if the policy key signed it and its version is higher than the bundled one, so whoever controls the host can withhold a newer policy (the bundled one stays in force) but cannot add a deployment the policy key did not sign. The policy key is a secret of this repository's `policy-signing` environment, limited to `main`. A scheduled workflow signs new compose hashes, new OS images and new measurements of NEAR AI's deployments, at most three times a day, each recorded in an issue. Before it signs, it reads the reports again under fresh nonces and verifies every entry (Intel quote and an `UpToDate` TCB, debug off, nonce and signer binding, event log, compose file); one entry that fails signs nothing. NVIDIA's GPU verdict is not checked in that job. Whoever can run workflows on `main` or take over the account can sign a policy. On testnet the owner accepts NEAR AI's word for the values: no reference NEAR AI publishes exists for them, a genuine quote does not say the software is safe, and a provider that ships faulty or hostile software is inside the accepted risk. Mainnet has not been decided. The model's compose hashes are pinned exactly; only the gateway's are not. A running `nymirad` 0.1.5 or later fetches the same file from the two hosts through its proxy every 15 minutes and takes it only when it verifies under the pinned policy key and its version is higher than the one in force; a stale or hostile host can only delay an update. Earlier `nymirad` releases do not fetch: their users copy the file by hand. An installed `nymirad` that is offline, or whose Tor is down, keeps its last policy and refuses chat for a deployment that policy does not list.
- **NVIDIA's attestation service (NRAS), directly or through the operator relay.** NRAS answers 403 to Tor exit nodes, so `nymirad` sends the GPU evidence to the operator, which forwards it to NRAS and returns the answer unchanged. The operator sees that some client asked for a GPU check, and when. It keeps nothing, and the lease is not part of the call, which uses its own Tor circuit. The operator cannot forge a verdict, because the client checks the token's signature, nonce and times, and that the signing key's certificate chain reaches a certificate pinned in the signed attestation policy. A relay that refuses only blocks a chat. With `--nras-direct`, NVIDIA sees the user's IP address and the time of each check instead. The signed policy (since version 5; version 9 is current) pins two NVIDIA intermediate certificates taken from NVIDIA's public key set on 5 November 2026; on 5 November 2026 the 005 certificate matched the copy served by NVIDIA's own PKI host (`prod.vault.nvidia.com`) and both verify under the root published there ("NVIDIA Attestation Service CA 001", SHA-256 `CDE269E3…1A1E`), but no NVIDIA documentation page lists the fingerprints, so the policy marks them unverified, and the root is not pinned. If NVIDIA rotates its intermediates, the check fails until a new signed policy is released. The web app does not ask NRAS, which refuses cross-origin requests. It checks the Intel TDX quote, the policy and the key binding, and says so.
- **1Click.** It sees the IP address of whoever asks for a quote, and the asset pair. The web app's testnet quote listing asks only after the user turns it on and sends no note data. `nymirad` sends testnet quote-only requests through Tor with placeholder accounts and no wallet or note data. Its mainnet funding path asks for explicit consent once per attempt, including after a restart, then calls 1Click directly outside Tor. On that path 1Click and the Intents explorer can pair the source wallet with the commitment and payout account. The quote signature identifies the issuer; 1Click and its solvers hold funds in transit, and the source wallet's refund address is the only way back. Spending can still be matched by timing and network address when few notes are open. No cross-chain payment is run on testnet.
- **Faucet.** Circle's faucet sees the account that asks for test USDC.

## What an encrypted request hides

`nymirad` and the web app encrypt every field the model reads to the model's attested key: message `content` and `name`, tool-call names and arguments, and tool names, descriptions and parameters. These stay in the clear because the operator and the gateway need them: the model name, `max_tokens` and `max_completion_tokens`, `stream` and `stream_options`, `n`, `temperature`, `top_p`, the two penalties, `seed`, `stop`, `tool_choice`, each message's `role`, `tool_call_id`, the `tools` key, the length of the `tools` array and each tool's `type`, and the sizes and timing of everything. The operator refuses a request with an unknown field instead of forwarding it. The browser cannot bind the gateway's TLS session, so the web app says "encrypted" on its own line and "model-signed" only when the signature checks.

## Trust in USDC

The vault holds Circle's USDC and trusts it fully. If Circle's blocklister blocks the vault account, closes, finalizes and claims stop; `request_exit` still works because it calls no token method, and payouts that cannot be sent wait in `pending_payouts`. Circle controls the token contract and can upgrade it or freeze funds. On testnet the token is Circle's testnet USDC and has no value.

## The trusted setup

The keys that check the zero-knowledge proofs come from a multi-party setup run by the team alone, with a public random value from a NEAR mainnet block applied at the end (the record and the scripts are in the nymira-ceremony repository). The setup is sound if at least one contribution kept its secret. We cannot show that from outside, and all contributions ran on the project's own machines. If it is not sound, someone who knows the combined secret can forge a proof and take what the vault holds. No loss of privacy is known from this. The proving keys are public files; the web app and `nymirad` check their SHA-256 against hashes shipped in the release. A vault made with zkapi's development keys or the rehearsal keys is for tests only and holds test funds.

## What the team's keys can do

The vault account keeps a full-access key. The team can use it to replace the vault code, so it could change the rules the contract enforces for deposits already inside it. The key is offline and the operator software never touches it. The operator account keeps its own full-access key offline too. Online work uses function-call keys whose methods are listed by name (`heartbeat`, `sync_root`, `mutual_close`, `defeat_exit`, `raise_concession`, `finalize_exit`, `retire_closed_leaf`, `claim_expired`, `claim_expired_batch`) and hold no owner method; the second machine's key has neither `heartbeat` nor `mutual_close`. Anyone can list a vault's keys with `view_access_key_list`, and `scripts/watch-vault-keys.mjs` raises an alert on a `DeployContract`, `AddKey` or `DeleteKey` on the vault account. The testnet vault caps open deposits, fees included, at 100 USDC, so a code swap by the team puts at most that much (test funds) at stake. The owner account can raise the cap 48 hours after announcing it, so the figure bounds the loss only while the cap stays.
